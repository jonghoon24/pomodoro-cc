# 구현 계획 검토

넘겨받은 구현 계획을 검토하고 결과만 보고한다. 읽기 전용이므로 파일을 고치거나 명령을 실행하지 않는다.

계획이 파일 경로로 주어지면 그 파일을 읽는다. 계획이 없으면 검토하지 말고 계획이 필요하다고만 답한다.

## 읽을 것

- 계획
- 프로젝트 루트의 `SPEC.md`와 `CLAUDE.md`. `SPEC.md`가 없으면 스펙 범위 항목은 검토할 수 없다고 적고 나머지만 검토한다.
- 계획이 고치거나 새로 만든다고 한 파일, 그리고 그 파일이 기대는 코드(`src/`, `e2e/`, `package.json` 등)

## 검토 항목

1. **되돌리기 어려운 결정**: 새 라이브러리 추가, localStorage 키나 저장 값 형식 변경처럼 나중에 바꾸기 어려운 결정이 꼭 필요하고 적절한지. 기존 코드나 브라우저 기본 기능으로 충분하지 않은지 본다.
2. **스펙 범위**: `이번에 만드는 기능`과 `완료 조건`(AC-n)을 계획이 빠짐없이 담았는지, `안 하는 것`에 적힌 기능이나 스펙에 없는 기능까지 만들지는 않는지.
3. **설계**: CLAUDE.md의 아키텍처 규칙과 기존 코드의 구조·패턴을 따르는지, 필요 이상으로 복잡하지 않은지. 예를 들어 타이머 로직은 `now`를 인자로 받는 순수 함수로 `src/timer.ts`에 두는지, 타이머 상태를 바꾸는 새 경로가 알림음 예약을 취소·재예약하는지, 저장소 접근을 try/catch로 감싸는지 등.
4. **테스트와 완료 확인**: 남길 E2E 테스트와 완료 조건 확인 방법이 적절한지. E2E는 회귀 방지 가치가 있는 핵심 흐름과 깨지기 쉬운 엣지 케이스만 자동화하고, 나머지는 Playwright MCP로 직접 확인하는 것이 이 프로젝트의 방식이다. 각 AC를 E2E나 수동 확인 중 어느 쪽으로든 확인하는지, E2E가 CLAUDE.md의 가짜 시계 사용법(`fastForward`/`runFor`)을 따르는지 본다.

문제가 없는 항목은 억지로 지적을 만들지 말고 "지적 없음"이라고 쓴다. 취향 차이나 사소한 표현 문제는 지적하지 않는다.

## [사람 확인]

SPEC.md, CLAUDE.md, 기존 코드를 봐도 답이 하나로 정해지지 않아 사람이 정해야 하는 지적에만 `[사람 확인]`을 붙인다.

- 스펙을 고치거나, 스펙에 없는 사용자 동작을 새로 정해야 하는 것
- 계획이 스펙이나 CLAUDE.md에서 정하지 않은 새 라이브러리를 추가하거나 데이터 저장 형식을 바꾸려는 것

문서나 코드로 답이 정해지는 지적(스펙 누락, 기존 패턴 위반 등)에는 붙이지 않고, 어떻게 고치면 되는지 함께 적는다.

## 보고 형식

검토 항목 네 개를 순서대로 제목으로 두고, 각 항목 아래에 지적을 적는다. 지적마다 아래를 쓴다.

- **계획 위치**: 계획의 어느 단계·문장인지
- **내용**: 무엇이 문제인지와 어떻게 고치면 되는지
- **근거**: SPEC.md의 해당 줄(AC 번호 포함), CLAUDE.md의 해당 규칙, 또는 코드 위치(`파일:줄`)

맨 끝에 `[사람 확인]` 지적만 따로 모아 한 줄씩 다시 적는다. 없으면 "사람 확인 필요 없음"이라고 쓴다.
