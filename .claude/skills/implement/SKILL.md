# 스펙 구현

프로젝트 루트의 `SPEC.md`를 구현한다. `SPEC.md`가 없으면 진행하지 말고 `/spec`으로 스펙부터 만들라고 안내한다.

## 1. 구현 계획

`SPEC.md`, `CLAUDE.md`, 관련 코드와 기존 E2E 테스트(`e2e/`)를 읽고 구현 계획을 세운다. 계획에는 아래를 적는다.

- **구현 방법**: 고치거나 새로 만들 파일과 각 파일에서 할 일
- **남길 E2E 테스트**: 새로 쓰거나 고칠 테스트와 각 테스트가 확인하는 완료 조건. 고르는 기준은 아래 [E2E 테스트 기준](#e2e-테스트-기준)을 따른다.
- **완료 조건 확인 방법**: AC마다 E2E 테스트, Playwright MCP 직접 조작 중 무엇으로 확인할지. 하나의 AC를 여러 방법으로 확인해도 된다.

## 2. 계획 검토

계획 전문을 `plan-reviewer` 서브에이전트에게 넘겨 검토받는다.

## 3. 지적 반영

지적마다 타당한지 직접 판단한다. 근거로 든 스펙 줄이나 코드 위치를 확인하고, 타당하면 계획에 반영하고 아니면 반영하지 않는 이유를 남긴다.

- `[사람 확인]` 지적이 하나라도 있으면 구현하기 전에 AskUserQuestion으로 사용자에게 묻고, 답을 계획에 반영한다.
- `[사람 확인]` 지적이 없으면 사용자에게 확인받지 않고 바로 구현으로 넘어간다.

## 4. 구현

계획대로 구현하고 E2E 테스트를 쓴다. 구현 중 계획을 바꿔야 하면 바꾼 내용과 이유를 기록해 두었다가 보고에 포함한다.

## 5. 완료 조건 확인

모든 AC를 실제로 확인한다.

- `npm run lint`, `npm run build`, `npm run test:e2e`를 실행해 모두 통과시킨다.
- E2E 테스트로 확인되는 AC는 해당 테스트 결과를 근거로 쓴다.
- 테스트로 확인되지 않는 부분은 `npm run dev`로 개발 서버를 백그라운드에서 띄우고 Playwright MCP로 앱을 직접 조작해 확인한다. 긴 시간이 필요하면 CLAUDE.md대로 집중·휴식 시간을 1분으로 설정한다. 확인이 끝나면 브라우저와 개발 서버를 종료한다.
- 확인 중 문제를 찾으면 고치고 관련 확인을 다시 한다.

## 6. 보고

아래를 보고한다.

- **완료 조건**: AC마다 통과 여부와 확인 근거(테스트 이름, 직접 조작한 절차와 관찰한 결과). 실제로 확인하지 못한 AC는 통과로 표시하지 않고 확인하지 못한 이유를 적는다.
- **검토 지적**: 반영한 지적, 반영하지 않은 지적과 그 이유, `[사람 확인]`에 대한 사용자 답
- **E2E 테스트**: 새로 쓰거나 고친 테스트와 각 테스트가 확인하는 AC
- **계획 변경**: 구현 중 계획과 달라진 점이 있으면 그 내용과 이유

## E2E 테스트 기준

AC마다 하나씩 쓰지 말고, 앞으로 기능을 더 만들어도 깨지면 안 되는 중요한 동작만 골라 쓴다.

- 사용자가 자주 쓰는 주요 기능이나 작업 흐름
- 다른 기능과 연결되어 있어서 변경할 때 깨지기 쉬운 동작
- 잘못된 입력을 막는 동작 중 대표적인 경우

테스트 하나로 AC 여러 개를 확인해도 된다. 이미 있는 테스트로 충분히 확인되는 동작은 새로 쓰지 않는다. 시간을 흘릴 때는 CLAUDE.md의 `page.clock` 사용법(`fastForward`/`runFor`)을 따른다.
