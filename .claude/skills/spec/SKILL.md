# 스펙 인터뷰

만들 기능:

$ARGUMENTS

위 내용이 비어 있으면 무엇을 만들지 먼저 물어본다.

## 인터뷰

AskUserQuestion 툴로 사용자를 인터뷰해서 이번 버전에서 만들어야 할 기능을 구체화한다.

- 각 기능이 어떻게 동작하는지와 엣지 케이스를 물어본다.
- 뻔한 질문은 하지 말고, 사용자가 미처 생각하지 못했을 부분을 파고든다.
- 질문하기 전에 CLAUDE.md와 관련 코드를 읽어 둔다. 코드로 이미 정해진 동작은 묻지 말고, 새 기능이 기존 동작과 부딪히는 지점을 묻는다.
- 한 번에 끝내지 말고, 답을 듣고 생긴 새 질문을 이어서 묻는다. 다 다뤘다고 판단되면 작성으로 넘어간다.

## SPEC.md 작성

다 다뤘으면 프로젝트 루트의 `./SPEC.md`에 작성한다. 이미 파일이 있으면 덮어쓰기 전에 사용자에게 확인한다.

형식은 [example-spec.md](example-spec.md)를 따른다. 제목 아래 다음 네 섹션을 둔다.

1. **목표**: 무엇을 왜 만드는지와 전제 조건(실행 환경, 언어 등).
2. **이번에 만드는 기능**: 기능별 하위 제목으로 나누고, 인터뷰에서 정한 동작과 엣지 케이스를 구체적인 값과 예시로 쓴다. 상태가 여러 개면 표로 정리한다.
3. **안 하는 것**: 인터뷰에서 빼기로 한 것과, 범위가 헷갈릴 만한 것을 적는다.
4. **완료 조건**: 아래 규칙을 따른다.

### 완료 조건 작성 규칙

- 한 항목에 "어떤 상황에서 무엇을 하면 무엇이 되는지"를 동작과 기대 결과로 쓴다.
  - 예: `집중이 10분 남았을 때 다른 탭으로 옮겨 12분 뒤에 돌아오면 휴식이 3분 남아 있다.`
- 테스트 코드처럼 쓰지 않는다. 셀렉터, 함수 이름, `expect`, 가짜 시계 조작 같은 구현·테스트 용어 없이 사용자가 보는 화면과 동작으로 쓴다.
- 자동 테스트로 확인하기 어려운 조건(실제 소리, 백그라운드 탭에서의 재생, 시각적 구분 등)은 끝에 `(직접 확인)`을 붙이고 목록 맨 끝에 모은다.
- 테스트 추가, 린트, 빌드, 테스트 통과처럼 매번 하는 확인은 CLAUDE.md에 있으므로 완료 조건에 넣지 않는다.
